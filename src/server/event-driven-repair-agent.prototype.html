Can one small durable model keep SMS, the repair agent, and manager approval in order?

This prototype tests whether a per-case event inbox, one serialized agent run, optimistic case revision, and a deterministic effect journal are enough for duplicate webhooks, overlapping replies, failures, restarts, human approval, and retry-safe real-world effects.

Throwaway prototype — no provider calls, credentials, persistence, or production code

Proposed event and state boundary

  1. 1. Verify and appendProvider signature, account, destination, role binding, and provider ID are checked before one event is stored.
  2. 2. AcknowledgeThe webhook returns immediately. Duplicate provider IDs point at the event already stored.
  3. 3. Run one caseA worker claims a high-water mark. New events wait; only one model run exists for the repair.
  4. 4. Commit by revisionModel tools and human commands bind exact case facts. A stale model write is rejected and rerun.
  5. 5. Dispatch effectsSMS, calls, and booking notifications use deterministic keys and a persisted delivery state.
